Uberblick / Docs / Sharing

Run a hub

A hub shares a workspace between computers. Every computer keeps its own copy and keeps working offline; the hub passes changes on and admits only the people who are members. You need one when a second person or a second machine should see the same documents. A hub is one Docker release: the hub itself and a Caddy web server in front of it.

Start one

Run this on the computer that will host it. It copies the release's files out of the hub image into ~/uberblick-remote, then starts the stack:

Terminal
$ mkdir -p ~/uberblick-remote && cd ~/uberblick-remote
$ HUB_VERSION=0.4.7   # a published release; nothing follows latest
$ docker pull --platform linux/amd64 "ghcr.io/uberblick-ai/hub:$HUB_VERSION"
$ release_container=$(docker create --platform linux/amd64 "ghcr.io/uberblick-ai/hub:$HUB_VERSION")
$ docker cp "$release_container:/release/." .
$ docker rm "$release_container"
$ cp remote.env.example .env && chmod 600 .env

$ sh bin/remote-compose.sh up --detach
$ sh bin/remote-compose.sh exec hub ub-hub status

The host needs Linux x86_64 with Docker Engine 28.0.0 or newer and Docker Compose 2.24.4 or newer, or Docker Desktop on macOS. Only linux/amd64 images are published, so Apple Silicon runs them under emulation. The host needs no ub client, no Node and no GitHub account.

The hub now answers at http://localhost:8080 and nowhere else: Caddy is published only on the host's loopback interface, and the hub has no port of its own. On its first start the hub creates one workspace, named Default workspace. bin/remote-compose.sh is a thin wrapper around docker compose that checks .env and picks the release's Compose files for the route you set there.

Claim it

Open http://localhost:8080 on the host and choose Sign in with GitHub. If the host has the client installed, this works too:

Terminal
$ ub auth login http://localhost:8080

The first GitHub account that completes sign-in becomes the hub's administrator and the administrator of its default workspace. The page and the terminal both report the claim and the workspace's UUID; keep the UUID, because every other computer needs it. Claim the hub before other computers can reach it. A claim cannot be handed over or undone. If the wrong account claims a fresh hub, start again with sh bin/remote-compose.sh down --volumes, which deletes everything on it.

Sign-in uses GitHub's device flow through the public Uberblick Login app, so there is nothing to register. GitHub's approval page shows the app's name, not your hub's: approve only a code you just started yourself.

Let other computers reach it

Choose a route in .env, then recreate the containers. All three routes admit the same signed-in members.

RouteSet in .envClients sign in at
This computer only, the defaultnothing; LOOPBACK_PORT changes 8080http://localhost:8080
Tailscale, recommended, Linux hostsWEB_HOST=machine.tailnet.ts.net
TAILSCALE_IP=100.x.y.z		https://machine.tailnet.ts.net
A public host nameWEB_HOST=hub.example.comhttps://hub.example.com
Terminal
$ sh bin/remote-compose.sh config --quiet   # refuses a bad setting and names it
$ sh bin/remote-compose.sh up --detach --force-recreate

Tailscale keeps the hub on your private tailnet. Turn on MagicDNS and HTTPS for the tailnet, then take the machine's full *.ts.net name from tailscale status --json and its address from tailscale ip -4. Port 443 is then published only on the Tailscale address, and Caddy gets its certificate from the host's Tailscale daemon. Enabling HTTPS in Tailscale writes the machine name to a public certificate log.

A public host name needs DNS records that reach the host and inbound TCP 443. Caddy gets and renews a publicly trusted certificate on port 443; port 80 stays closed. IP addresses, local names and your own certificate files are not supported.

Changing routes keeps the documents, the claim and the certificates, which live in the hub-data, caddy-data and caddy-config volumes. Clients sign in again at the new address.

Connect a computer

On each computer that should use the hub's workspace, in the project directory:

Terminal
$ ub auth login https://hub.example.com
$ ub workspace use wss://hub.example.com/ws/<WORKSPACE_ID>
fetched    Product notes from https://hub.example.com: 12 documents
using      Product notes (<WORKSPACE_ID>, https://hub.example.com)
wrote      ~/Projects/project/.uberblick.json
open it with: ub open

ub auth login stores a device login for that hub on this computer. It lasts 30 days and renews itself while the client is in use; it changes nothing else. ub workspace use downloads the whole workspace, checks it, and only then binds the project to it. The MCP server and ub open follow that binding. Spell the hub's address the same way everywhere: localhost and 127.0.0.1 are different hubs to the client.

Already have a local workspace to share? Sign in as a hub administrator and run ub workspace promote https://hub.example.com in its project. It uploads every document, verifies them on the hub and binds the project, then prints the link for the other computers.

Other people sign in the same way, but a hub admits only members. A workspace administrator adds them with ub workspace member add <github-handle>; see Access and membership.

Check, back up and update

The hub image carries ub-hub for everything an operator does inside it. Run these in ~/uberblick-remote:

Terminal
$ sh bin/remote-compose.sh exec hub ub-hub status   # release, protocol, database, claimed or not
$ sh bin/remote-compose.sh exec hub ub-hub doctor   # ok, warn, FAIL or skip per check, changes nothing
$ sh bin/remote-compose.sh logs --tail=100 hub caddy

$ sh bin/remote-compose.sh exec hub ub-hub backup   # while the hub keeps serving; prints the file
$ sh bin/remote-compose.sh cp hub:/data/<backup-file>.sqlite ~/uberblick-hub-backup.sqlite

$ sh bin/remote-compose.sh stop hub
$ sh bin/remote-compose.sh run --rm hub ub-hub restore /data/<backup-file>.sqlite
$ sh bin/remote-compose.sh start hub

A backup is a verified copy of the hub's database: documents, claim and access records. Keep it private, and copy it off the host, because a copy left in hub-data is lost with that volume.

The hub never updates itself. To move to a newer release, back it up, copy the new release's files over the old ones the same way you started, and recreate. .env is never part of a release, so your settings stay:

Terminal
$ cd ~/uberblick-remote
$ HUB_VERSION=0.4.7   # the release you are moving to
$ mkdir ".release-$HUB_VERSION"
$ docker pull --platform linux/amd64 "ghcr.io/uberblick-ai/hub:$HUB_VERSION"
$ release_container=$(docker create --platform linux/amd64 "ghcr.io/uberblick-ai/hub:$HUB_VERSION")
$ docker cp "$release_container:/release/." ".release-$HUB_VERSION/"
$ docker rm "$release_container"
$ cat ".release-$HUB_VERSION/release.json"   # version, source commit, sync protocol
$ cp -R ".release-$HUB_VERSION/." .
$ sh bin/remote-compose.sh pull
$ sh bin/remote-compose.sh up --detach --force-recreate

Each release ships the client and the hub from the same commit. When the sync protocol in release.json changes, update the hub and every client in the same sitting; an older client is told an update is required. If you cannot do both now, do neither.

What a hub does not do

  • It serves no documents to a browser. Its web page signs you in and shows how to connect; you edit through ub open or your agent, on your own computer.
  • It does not take back what a computer already downloaded. Removing a member stops their sync, not their local copy.
  • It does not update, restart or back itself up on a schedule. Every change to the host is an operator's command.
  • It runs once per Docker host, managed from a session on that host. Remote orchestration is not supported.

Every setting, route, recovery step and upgrade note is in REMOTE.md, which each release also copies into ~/uberblick-remote.
