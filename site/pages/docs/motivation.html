Motivation

Uberblick, ub-agents, the skills and the small libraries beside them come from one team in Berlin running its own software with coding agents. None of them started as a product. Each was extracted from that work because something in it kept hurting; good frameworks are extracted, not planned. This page says what, once, so the other pages don't have to.

The premise

People and coding agents working in the same codebase is the new reality. The agents are capable, but they are only as good as the context they get: what the product should do, what was decided and why, what the numbers say. Much of that knowledge lives only in local artefacts and is rarely shared. Where it is shared, it is scattered across tools, and those tools were not built agent and MCP first.

Our bet is one place for delivery, GitHub, where issues, pull requests, labels and Actions already carry the work and every agent can read and write them today, and context that agents and people reach alike, each in the form that suits them: documents and records over MCP for the agent, a page in the browser for the person. What GitHub lacks is a home for that reasoning and those records. That is what we build, so a team can run on GitHub alone, with nothing else to keep in sync.

Uberblick

Markdown files in the repo go stale, and the planning a person does with an agent on their own machine rarely leaves it. What agents write is often a wall of text that nobody scans. Uberblick is a workspace of documents that both people and agents edit: local first, because the documents belong on the team's own computers, and MCP first, because an agent gets the same documents, through the same tools, as a person in the browser.

The split is simple. GitHub issues and pull requests carry the work. Local Markdown stays what it is, notes for one person and one agent. The Uberblick workspace holds what the team has to share and keep true: the product intent, the plans, the delivery reports and the numbers behind them. Because agents write most of it, Uberblick puts its effort into a few Markdown additions that let an idea be drawn instead of described: a flow, a screen, a chart from the data it explains. Decisions get a small record of their own along the way, so an agent can ask which ones touch its issue. A hub, one Docker container, syncs a workspace to the people you share with. Start here.

ub-agents

Autonomous agents are the reality for an engineering team now. Guiding a model through an interactive session is worth it only where a decision or a person's feedback matters in the moment; most work can be dispatched as a workflow. ub-agents is a loop engineering framework for GitHub: roles defined in a few lines of YAML, driven by labels, so issues get prepared, implemented, reviewed and merged by agents, and a person steps in only where a label says so. It runs on GitHub Actions with any agent and no server, because the loop should live where the issues live.

Every run starts with fresh context. The agents have no memory, only what their local Markdown files and Uberblick hand them, so a gap in the documentation shows up in the next run instead of staying hidden. Each agent ends its run with a short retrospective on what would have made it more efficient, and the loop feeds that into the next run, so it learns from its own work. Uberblick is built this way: its product intent sits in an Uberblick workspace, and the loop's agents read it over MCP before they prepare, implement or review an issue.

Skills

A loop that needs a person for every item isn't a loop. The evidence of how it did is already on GitHub, in claims, outcomes, retries and retrospectives, but reading it by hand takes longer than the runs did. The skills read it for you: they report what the loop delivered, what it cost, what it is waiting on, and propose the smallest change that fixes it, usually by removing scope or text rather than adding another rule. They follow the Agent Skills specification, so they work in Claude Code, Codex and the other agents that support it.

The small libraries: ablauf and wireframe

Some things a team needs to say are drawings: how a flow runs, what a screen looks like. The diagram formats we tried were either too hard for an agent to write without breaking them or too hard for a person to read as text. ablauf is a small text format for flow diagrams in which the author, usually an agent, decides the layout and the renderer only draws and reports problems; it replaces Mermaid in Uberblick. wireframe aims at the same for screen sketches, starting from the ASCII sketches people already draw in issues. Both are early, and both exist to keep drawings inside the document, next to the words.

Build your own variant

None of this is meant as the one right answer. It is what held up for one team, released as a framework and a few products under the MIT license so you can take the parts that fit and change the rest. The repositories are on GitHub.
