# Embeds spike: findings

Run on 2026-10-10 on a Mac (Playwright 1.62.1: Chromium 151 headless shell,
WebKit, Firefox 153), harness on `http://127.0.0.1:4599` with the CSP from
`serve.mjs`. Phase 2 ran in Chromium against the e2e harness (`ub open` and the
hub on free ports). Evidence is in `results/`: `summary.md` and `results.json`
for phase 1, `<browser>/cN.png` screenshots, `interaction-proto/` for the
interaction check on a prototype, and `phase2/` for the editor run.

Short version: variant A works. Public Figma design frames, prototypes,
FigJam boards and community files embed from `127.0.0.1` with the proposed
attributes. YouTube and Loom work in the same frame, but YouTube needs a
referrer. The shield makes the frame inert until clicked. The node view keeps
its iframe through typing, remote edits, agent edits, undo and theme changes.
Only the client that moves the block reloads it. Three things need design work:
- Figma's bot defence makes automated tests unreliable.
- `load` cannot detect a broken link.
- Many live Figma embeds on one page run out of WebGL contexts and memory.

## 1. Do public Figma links embed from 127.0.0.1? Which kinds? **Yes**

All four kinds render with `sandbox`, `referrerpolicy=no-referrer`, `allow`,
`embed-host=uberblick`, `footer=false` and `theme`, wherever Figma's bot
defence lets the browser through:

| Kind | Chromium (headless) | WebKit | Firefox |
| --- | --- | --- | --- |
| Design frame | 403 from CloudFront (`chromium/c3.png`) | renders (`webkit/c3.png`) | renders (`firefox/c3.png`) |
| Prototype | renders (`chromium/c4.png`) | renders | renders |
| FigJam board | 403 (`chromium/c5.png`) | renders (`webkit/c5.png`) | renders in run 2, still loading at screenshot time in run 3 (`firefox/c5.png`) |
| Community, candidate 1 `embed.figma.com/community/file/<id>` | 403 | WAF challenge loop: "Max challenge attempts exceeded", 6 × HTTP 202 (`webkit/c1.png`) | renders (`firefox/c1.png`) |
| Community, candidate 2 `www.figma.com/embed?url=…` | 403 | same challenge loop (`webkit/c2.png`) | renders (`firefox/c2.png`) |

- **The Chromium 403 is a headless artefact, not a refusal.** The page reads
  "Request blocked … Generated by cloudfront". I did not spoof a user agent.
  The app's own browser pane (a real, non-headless Chrome 152) loaded the same
  `embed.figma.com/design/…` URL as a normal page. Top-level, it redirects to
  the full `www.figma.com/design/…` editor. Figma does not block Chromium, only
  headless Chromium.
- **WebKit's community-file failure is Figma's AWS WAF challenge** (HTTP 202,
  retried until it gives up). Firefox passes the same challenge. It may also
  hit real Safari users on community links. Worth a manual Safari check.
- **Community candidates:** both forms redirect to the same
  `www.figma.com/file/…` viewer and behave identically. Use candidate 1, the
  documented `embed.figma.com` domain.
- **The redirect chain matters for CSP:**
  `embed.figma.com/design 302 → www.figma.com/embed 200 → (script) www.figma.com/embed 302 → www.figma.com/design 200`.
  So `www.figma.com` must be in `frame-src`, and every working Figma embed
  fires **two** `load` events.
- **`theme=dark`** only darkens Figma's own controls (zoom and logo buttons).
  The canvas keeps the file's own background (`webkit/c12.png`,
  `firefox/c12.png`).
- **Recommendation:** run automated Figma proofs on prototypes, which pass in
  headless Chromium too, or in WebKit and Firefox. Treat Chromium design and
  board results as a manual check.

## 2. Same frame for YouTube and Loom? Does YouTube need a referrer? **Yes, and yes**

- YouTube (`youtube-nocookie.com/embed/<id>`) renders the poster in all three
  browsers with `referrerpolicy=strict-origin-when-cross-origin` (`*/c7.png`).
- With `no-referrer` it shows **"Video player configuration error, Error 153"**
  in all three browsers (`*/c8.png`). The player's own stats ping logs
  `error=…embedder.identity.missing.referrer`. **YouTube needs a referrer.**
  The origin is enough: `strict-origin-when-cross-origin` sends only
  `http://127.0.0.1:4599/` across origins.
- Loom (`loom.com/embed/<id>`, `no-referrer`) renders the player in all three
  browsers (`*/c9.png`).
- WebKit logs "'allow-presentation' is an invalid sandbox flag". It is
  harmless, but drop it, because `allow="fullscreen"` covers fullscreen.

## 3. Does the sandbox break anything? **No difference seen (partly tested)**

The design frame with and without `sandbox` renders identically in WebKit and
Firefox (`*/c3.png` against `*/c11.png`). One earlier Firefox run left the
no-sandbox copy blank, and the next run rendered it, so the blank was
flakiness, not the sandbox. Sandboxed prototypes navigate, and YouTube and Loom
show their players. Not tested: playing a video to the end, Figma's "Open in
Figma" popup (it needs `allow-popups` and `allow-popups-to-escape-sandbox`,
which the proposed set includes) and signed-in private files.

## 4. Inert until clicked, click activates, Escape, click outside? **Yes**

From `results/interaction-proto/summary.md` (prototype, all three browsers)
and `results/summary.md` (design frame):

| | Chromium | WebKit | Firefox |
| --- | --- | --- | --- |
| Wheel over inert frame scrolls the page | yes | yes | yes |
| Click activates (focus moves to the `IFRAME`) | yes | yes | yes |
| Wheel over active prototype stays in Figma | yes | yes | yes |
| Wheel over active design frame stays in Figma | n/a (403 page) | yes | **no, the page scrolled** |
| Escape reaches Uberblick while Figma has focus | no | no | no |
| Click outside releases | yes | yes | yes |

As expected, Escape never reaches the parent once the frame has focus, so
releasing needs the outside click or a visible "Done" control. Firefox let the
wheel through on the design viewer but not on the prototype. That is Figma's
viewer, not our frame.

## 5. Does `loading="lazy"` hold off the request inside a nested scroller? **Partly**

The probe is a YouTube embed 2400px down inside a 360px scroll container that
is itself on screen. I checked the iframe's own frame URL before and after
scrolling the container:

- WebKit and Firefox: nothing loaded before the scroll (`frameUrl ""`, 0
  loads), and it loaded after (`results/summary.md`, Lazy lines).
- Chromium: **already loaded before the scroll.** Chromium's lazy-load
  distance is wide enough to cover 2400px.

So `loading="lazy"` is not enough on its own for a long document with many
embeds. Pair it with our own `IntersectionObserver` on `.ub-document-pane` and
a small `rootMargin`, and set `src` only when the frame comes near.

## 6. Does the `frame-src` allowlist work? **Yes**

The provider list (`embed.figma.com www.figma.com www.youtube-nocookie.com
www.loom.com`) let every provider through. Their redirects included, no
violation for them. `https://example.com/` was blocked in all three browsers
(`securitypolicyviolation`: `frame-src https://example.com`, `*/c13.png`
blank). In Chromium and WebKit, the blocked iframe **still fired `load` once**.
Firefox fired none.

## 7. What does a broken Figma link look like? Does `load` fire? **A Figma error page; yes, `load` fires**

`embed.figma.com/design/AAAA… 302 → www.figma.com/embed 404`. The frame shows
Figma's "Whoops! We can't seem to find that … Figma only allows publicly
accessible files to be embedded" page (`*/c6.png`), and `load` fires once.
A private file gets the same page. The parent cannot read a cross-origin frame,
and blocked frames fire `load` too (question 6). **So `load` cannot tell
success from failure.**

What does work is **oEmbed**. All three providers answer CORS requests from the
page:
- Figma `https://www.figma.com/api/oembed?url=…` returns 200 with title and
  thumbnail for public files, and 404 for missing or private ones
  (`access-control-allow-origin: *`).
- YouTube `https://www.youtube.com/oembed` echoes the origin.
- Loom `https://www.loom.com/v1/oembed` sends `*`.

One request gives the caption title, a poster for the inert state, and a
"not public" message before any iframe loads. The cost: `connect-src` for those
three endpoints and `img-src` for their thumbnail CDNs. Alternatively, `ub` can
fetch oEmbed server-side.

## 8. In the editor: same iframe across edits? What CSP does the app need? **Yes, except for a local move**

Throwaway node view: `packages/web/src/editor/embed-spike.ts`, wired into
`CodeBlock` in `nodes.ts`, and test `packages/web/e2e/embed-spike.spec.ts`.
The test seeds `p, Figma prototype, p, YouTube, p` through MCP, opens it in two
browser contexts A and B, waits 6s after each step, and diffs the probe
counters (`phase2/reloads.json`):

| Step | A: view created / destroyed / iframe loads | B | Order afterwards |
| --- | --- | --- | --- |
| Type in the paragraph above (A) | 0 / 0 / 0 | n/a | p Figma p YouTube p |
| Type between the embeds (A) | 0 / 0 / 0 | n/a | same |
| Second client types (B) | 0 / 0 / 0 | 0 / 0 / 0 | same |
| MCP agent edits a paragraph | 0 / 0 / 0 | 0 / 0 / 0 | same |
| Move the Figma block below the next paragraph (A, delete + insert like a drag) | **1 / 1 / 2** (new view, one Figma reload = two loads) | 0 / 0 / 0 | p p Figma YouTube p |
| Undo the move (A, Mod+z) | 0 / 0 / 0 | 0 / 0 / 0 | p Figma p YouTube p |
| Switch theme (`data-theme=dark`) | 0 / 0 / 0 | 0 / 0 / 0 | same |
| Edit the YouTube URL (expected) | 0 / 0 / 1 (src changed) | 0 / 0 / 1 | same |

- **Typing, remote edits, agent edits, undo and theme changes never reload an
  iframe.** On those updates, `update()` keeps the view and the src is
  unchanged.
- **Moving reloads, only for the mover.** The local move is a delete plus an
  insert of the embed node, so ProseMirror builds a new view (instance 3) and
  a new iframe. The remote client and the undo get the same order change, but
  ProseMirror moves the neighbouring paragraph's DOM instead, and the iframe is
  never re-attached. Any DOM re-attachment of an iframe reloads it in every
  engine. A real move feature should either accept one reload for the mover,
  or move the paragraphs around the embed.
- **Theme:** the src carries `theme`, so following a theme switch means a
  reload. The spike reads the theme once at creation, and since `theme=dark`
  barely changes Figma (question 1), following it is not worth a reload.
- Screenshots: `phase2/a-seeded.png`, `phase2/a-after-edits.png` (dark,
  after all steps, both embeds rendering in the editor).

**Report-only CSP** added to `ub open` (`packages/cli/src/open.ts`):
`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:;
font-src 'self'; connect-src 'self'; frame-src <providers>; object-src 'none';
base-uri 'self'; form-action 'self'`. Violations across both clients
(`phase2/csp-report-only.json`):

| Directive | Count | Source |
| --- | --- | --- |
| `script-src-elem` inline | 2 (once per page) | the appearance snippet in `index.html` (line 7). Chromium suggests hash `sha256-YjJtHnJO51MquaKg9QRoM0GV291vCKejgzvWQIQbiYo=` |
| `style-src-attr` inline | 18 | inline `style` attributes set from the app bundle (`index-*.js`). Some are from the spike view, which uses `style.cssText`, but Radix, Floating UI and Chart.js also write inline styles |
| `style-src-elem` inline | 4 | `<style>` elements injected by the bundle |

No `connect-src` violation (the serving-replica websocket counts as `'self'`),
none for fonts, images or frames.

## Recommended iframe attributes

```
<iframe
  src="(built by Uberblick from the pasted link, never the pasted string)"
  title="Figma: <oEmbed title>"
  sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms allow-storage-access-by-user-activation"
  allow="fullscreen; clipboard-write"            (YouTube: add "picture-in-picture; encrypted-media")
  referrerpolicy="no-referrer"                   (YouTube: "strict-origin-when-cross-origin", required)
  loading="lazy"                                 (plus our own IntersectionObserver gate, question 5)
  allowfullscreen>
```

Figma URL parameters: `embed-host=uberblick`, `footer=false`, keep `node-id`
and `starting-point-node-id`, and `page-selector=false` for frames. Leave
`theme` alone or set it once. Do not add `allow-presentation`.

## Recommended CSP for the web app

```
default-src 'self';
script-src 'self';                    (move the index.html appearance snippet to a file, or add its sha256)
style-src 'self' 'unsafe-inline';     (needed by the libraries' inline styles; style-src-attr cannot use hashes)
img-src 'self' data:;                 (+ oEmbed thumbnail hosts, if posters are used)
font-src 'self';
connect-src 'self';                   (+ the three oEmbed endpoints, if fetched from the browser)
frame-src https://embed.figma.com https://www.figma.com https://www.youtube-nocookie.com https://www.loom.com;
object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

Ship it report-only first. Phase 2 covered `ub open` in Chromium only, so the
hub-served client, the dev server and Safari still need a pass.

## Surprises

- **Figma's bot defence** (CloudFront 403 for headless Chromium, AWS WAF
  challenge loops in WebKit) is the biggest obstacle to automated proof, and
  possibly a real-Safari issue for community links.
- **Every Figma embed is heavy.** With eight Figma viewers on one page,
  WebKit logged "There are too many active WebGL contexts on this page, the
  oldest context will be lost". Firefox logged
  `compileStreaming compiled_wasm.wasm failed: InternalError: out of memory`
  and `MobileFileViewer: failed to initialize`, which probably explains its
  occasional blank or still-loading Figma frames. A document with many Figma
  blocks needs a poster (oEmbed thumbnail) and a click or near-viewport gate,
  not N live viewers.
- **Firefox rejects Figma's cookies in the cross-site frame**
  (`figma.session`, `__Host-psifi…`, `product_locale`). Public embeds still work. Private files
  will depend on `allow-storage-access-by-user-activation` and the Storage
  Access API, which is the manual signed-in check still to do.
- **Two `load` events per Figma embed** (the embed page navigates itself), so
  any "loaded" indicator must not count loads.
